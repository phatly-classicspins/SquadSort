# Visual design — a surface ships finished

Verbatim rule: **`docs/framework/AGENTS.framework.md` §1 rule 17**. Origin and rationale: brief
**§8.7**. Geometry and the ruler this all sits on: the `pf-world-space` skill.

> **The human/machine zone boundary is about mechanism, not authority.** It says a prefab is edited
> through the live editor (raw YAML corrupts GUIDs). It never said the *look* is not yours to decide.

Rule 17 covers **shipping player-visible surfaces**. It is not retroactive: editing a legacy screen
does not oblige you to retrofit it, and editor-only or debug-only UI is out of scope.

## The authority ladder — stop at the first rung that answers

| Rung | Source | What it binds |
|---|---|---|
| 1 | **Artist spec** — `docs/art-direction.md` | Follow it. Any deviation is named in the spec's Design Notes, never silent. |
| 2 | **The SKU's existing look** — its prefabs and its `LookLibrary` | A second feature must not invent a second palette. The existing look binds you like an artist spec would. |
| 3 | **You** | No spec, no established look ⇒ decide, then **record it on the prefab + the `LookLibrary`**. An undocumented choice is a rung-2 failure for the next feature. |

Only `docs/art-direction.md` and "the prefab + one LookLibrary per SKU" come from the verbatim rule. The extra probe
paths (`docs/art/*.md`, `Assets/{sku}/Content/art-direction.md`) and the look-recording conventions below are
**convention, not contract** — useful defaults, but a SKU that puts them elsewhere is not in breach.

**An approved mockup is rung 1 for size and type.** When the SKU has an approved UX package (bmad-ux
mockups + DESIGN.md), the **mockup outranks the numbers written in the design documents** for visual
size and type at the 1080 reference — row heights, title sizes, panel heights, icon and art sizes, type
weight. The design documents still outrank the mockup for behaviour, flows, rules and content order.
Measured on one SKU: DESIGN.md's 168-px settings row (≈180 px pitch) against the mock's ≈110 px pitch
pushed three Settings rows below the fold, and every review ranked the document above the picture.
A **touch-target minimum is met with an invisible, expanded hit area** (a transparent raycast target
larger than the visual), never by enlarging the visual; where neighbouring targets cannot reach the
floor without overlapping, ship the mock's size and report it. A design-doc size that must beat the
mock needs a `DIVERGENCES.md` row carrying a human decision. **Copy in a mockup is illustrative** —
its wording, extra lines and data values are never a target; the style and size of that text are.

**When rungs collide:**
- An artist spec that lands *after* tokens exist **supersedes** them — rewrite the prefabs and the LookLibrary in the
  same change, rather than leaving the palette split between two sources.
- Rung 2 missing a value the new feature needs ⇒ **extend the LookLibrary (a shared, data-chosen value) or author it on the prefab in that change**. Declaring
  a local literal "just this once" is the exact shape rule 17 rejects.

## Where the look lives — the prefab, then one LookLibrary

| Value | Lives in | Edited by |
|---|---|---|
| A node's rect (anchors, pivot, position, size, scale), its Graphic colour, its TMP font / size / material | **the prefab** | a human in Prefab Mode, or an agent through Unity-MCP (rule 12) |
| A value shared across prefabs **and chosen by data at runtime** — the palette a group colour indexes, plates, button tiers, type roles, the scrim, markers | **one `LookLibrary` asset** per SKU (conventionally `Assets/{sku}/Content/UI/Look/LookLibrary.asset`), Inspector-edited, injected | the Inspector |
| Durations, eases, delays | **`Assets/{sku}/Views/MotionTokens.cs`**, a `static class` | code |

**Why the prefab and not a token file.** When every size is written from a C# constant on bind, a dev
who edits the prefab and saves sees the edit overwritten, changing a look means editing a giant C#
file, and a field assertion that pins the constant proves only that the View copied it. The prefab is
what the person looking at the screen edits, so it is the single source: **a View never writes a look
value its prefab holds.** Code writes only what **data** decides — a list's height from its row count,
a group's tint from its id — and the node that carries it is marked `LayoutDriven(<properties>)`.

**What guards it — three rungs, none of them a pinned number.**

1. **The layout snapshot.** A Prefab Mode save (and nothing else but the bootstrap menu
   `Framework/UiGate/Snapshot All Prefab Layouts`) writes `Tools/UiGate/layout/<prefab path>.json` —
   local rect + look fields per node, `prefab-layout-snapshot/v1` — for that prefab and every prefab
   that nests it. A test binds the View to fixture data and asserts
   `PrefabLayoutAssert.Diff(instance, prefabPath)` is empty: a non-driven property that differs was
   *written by code after bind*; a prefab that differs from its snapshot was *changed outside Prefab
   Mode — re-save in Prefab Mode if intended*. Never hand-edit a snapshot. Doctor check 17 reports a
   missing or stale one as Drift.
2. **The layout lint.** `PrefabLayoutAssert.Lint(root, extent)` against `Tools/UiGate/ui-rules.json`,
   under `PrefabLayoutAssert.Host(extent)` at each of `base` / `tall` / `wide`: content inside the
   visible rect by `pad`, Selectable hit area ≥ the touch floor, no overlapping sibling controls, label
   fit, font size ≥ the floor. Relations and floors — never a position. A finding names node, rule and
   extent; an exemption in the rules file carries a reason.
3. **The UiGate.** A probe reads its expected colour off the prefab's own Graphic
   (`CaptureProbePoint.FromGraphic` emits `#RRGGBB`), so no token file is needed to settle it.

**Read the node, never a mirror of it.** A dynamic layout reads its inputs off the nodes (a row's height is its own
rect, a text's start size its own `fontSize`), once before its first write, and writes only the driven property. A
serialized struct of sizes copied onto the nodes is a token file by another name: the prefab edit is still overwritten.
Only a gap no node holds is a serialized field. `PrefabLayoutAssert.EditSurvivesBind` is the test that tells them apart.

So a relation test (the list is as tall as its rows, the label fits its pill) is how a driven value is
held; an absolute number in a test is a change detector the next restyle rewrites.

**Never** a `Color`, hex literal, or bare spacing number in a View. Views read the look off the prefab,
or a shared value from the `LookLibrary`. A controller may still choose *which* entry —
`Game.Presentation` references `Game.Views`, so that compiles — but the View alone decides how it is
drawn (rule 8).

## Deciding with no spec

**Palette — build it as steps, not as favourites.** Pick a **ground**, then a **surface** one visible
step off it, then a **slot** tone between surface and content. Content sits clearly above surface in
lightness. One accent hue, reserved for the primary action. Text gets exactly two tones, chosen by a
stated threshold rather than by eye: fill **relative luminance ≥ 0.5 ⇒ `TextOnLight`**, below ⇒
`TextOnFill`.

**Setting the ground is a SKU job, and it has a specific mechanism.** The rig camera's clear colour
is Master-Scene rig work — **Ask-First**, so it is not your lever. Draw the ground instead: a
full-bleed sprite sized from `IWorldViewport` (read at the use site, never cached), parented under the
scene's `WorldRoot`, `Stamp`ed onto the lowest-order render layer that draws, with the lowest
`sortingOrder` in it. Details in `pf-world-space`. A rig default reaching a player is the tell that
nobody chose a ground at all.

**Spacing — one atom, everything an expression over it.** Choose `Unit`; author every gap and pad on
the prefab as a multiple of it. A slot gap reads well at roughly **10–15% of the slot**;
below ~8% the grid looks cramped and merged.

> **Do not let the safe rect pick your ratios.** Solving `n·cell + (n+1)·gap ≤ 1080` for `gap` is how
> a grid ends up at 8%. Choose cell and gap for rhythm first, then fit — `IWorldViewport` and the
> scaler exist so the *view* adapts to the design, not the design to a constant (`pf-world-space`).

**Type — three sizes per surface, at most.** Label, value, title. The primary value is ≥ 2× its label,
or the pair reads as one flat string.

**Type roles, built on static weights.** Text is drawn through **roles** (Display, Title, Subtitle,
Body, Label, Caption — name your own), never as an ad-hoc font + `fontSize` pair. A role token carries
everything that makes text look like the design: the **TMP font asset**, the **size**, a **material
preset** (outline / underlay — headline roles only), the **letter case** and the **colour**. A View
applies the role; a View that sets a bare `fontSize` or swaps a font asset is a rung-2 failure.

> **TMP cannot draw a variable font's other weights.** A TMP font asset built from a variable font
> (`Nunito[wght].ttf`, any file with an `fvar` table) renders that file's **default instance** — and
> setting `fontWeight` or a role called "Black" changes nothing. Measured on one SKU: DESIGN.md asked
> for Nunito 800/900, the source was `Nunito[wght]` whose default is **200 (ExtraLight)**, and all 170
> texts in the game shipped ExtraLight — with every Visual Contract row passing, because no row looked at
> weight. Build one static instance per weight a role uses (`Tools/pf/font-check.py --instance <font>
> --weights 800,900`) and a TMP font asset from each, fallbacks included (a Thai fallback that is
> variable draws its own default weight next to your Latin). `Tools/pf/font-check.py --check` runs inside
> `gate.sh` leg 1 (`greps.sh` check `variable-font`) and fails on any variable source, fallbacks
> included. Rebuild each TMP asset from its static `<Family>-<Weight>.ttf` (spaces dropped:
> `NunitoSans-800.ttf`) through the Font Asset Creator via Unity-MCP; `--instance` needs fontTools and
> runs itself through `uv` when it is missing. A heavier weight is wider (+8–16% from 200 to 900 on Nunito):
> re-run every label-fit assertion after the change, and check the SDF padding still covers the
> headline outline + underlay.

**Prove the roles once, on a specimen.** The first presentation story renders a `type-specimen`
capture surface — every role, plus the button / panel / ribbon families — and judges it against the
approved mockups with blocking `[type]` / `[scale]` rows (`docs/framework/recipes/visual-contract-judge.md`).
A systemic error (a wrong weight, a wrong scale) is stopped there, at the first story, instead of
surfacing on every screen at the end.

**`fontSize` is a world-unit measure on this rig — size it from the box, never from a remembered
number.** The ruler runs all the way through type (`pf-world-space`): a host canvas is at
`referencePixelsPerUnit 1` and `localScale 1`, and `TextMeshProUGUI.Awake()` sets `isOrthographic =
true` unconditionally, so TMP's font scale carries **no** extra multiplier —
**`1 TMP font point == 1 design px == 1 world unit`**. Measured on LiberationSans SDF: a line box is
`1.117 × fontSize` units, a digit advances `0.558 × fontSize`, a cap height is roughly `0.7 ×
fontSize`. So a value filling about half a 240-unit slot is `fontSize ≈ 170`, and a **four-digit
`fontSize` is a red flag**: at 1500 a single line box is 1675 units — 87% of the 1920-unit safe height,
which only a full-screen countdown digit could want. These ratios move with the font, so measure once
per font and store them as tokens next to the sizes they derive.

> **The one thing that breaks the 1:1 ruler — and a bigger `fontSize` is the wrong fix.** A
> **Renderer-drawn** `TextMeshPro` (3D text under `WorldRoot`, no canvas) keeps TMP's serialized
> `isOrthographic = false`, and TMP then scales the font by **0.1**
> (`TMP_Text.cs`: `orthographicMultiplier = m_isOrthographic ? 1 : 0.1f`) — a digit lands at
> `0.073 × fontSize` and the text reads 10× too small. Inflating the token to ~1500 hides the symptom
> and leaves every metric off by 10×. **Tick Orthographic Mode (`isOrthographic = true`)** on that
> component — the rig camera *is* orthographic — and the 1:1 ruler holds there too.

**Measure it, do not remember it.** Before a type token is written down, get the ratio off the rig
with one `script-execute` on the object you just built:

```csharp
// Units per font point, for THIS font, on THIS rig. Expect ≈1.117 / ≈0.558 (LiberationSans SDF).
var t = GameObject.Find("ScoreValue").GetComponent<TMPro.TMP_Text>();
t.enableAutoSizing = false; t.fontSize = 100f; t.ForceMeshUpdate();
var v = t.GetPreferredValues("0");                       // canvas units == world units here
Debug.Log($"per point: advance={v.x / 100f:0.###} lineBox={v.y / 100f:0.###}");
```

A value that must survive its longest string needs `enableAutoSizing` plus a floor derived from that
advance, not a smaller size everywhere: four digits inside a 210-unit slot fit at
`4 × 0.558 × 70 = 156` units, so the floor token is `70`.

> A label-over-value pair is **two** text objects, not one formatted string. Rule 4 still holds: the
> label is a `LocKey`, the number is a `CultureInfo.InvariantCulture` formatted value needing none.
> "Score: 0" as a single localized line is a hierarchy you cannot build.

## The finished-surface checklist

Walk all nine before calling anything done. Each is decidable — no taste required.

| # | Check | Fails when |
|---|---|---|
| 1 | **Ground** | The rig default reaches the player, or no object draws the ground. |
| 2 | **Containment** | A container that holds slots draws no empty slots — a bare panel. |
| 3 | **Rhythm** | A spacing number is written by View code instead of authored on the prefab, or the layout lint (`ui-rules.json`: pad, touch floor, sibling overlap) reports a finding at any extent. |
| 4 | **Hierarchy** | >3 type sizes on one surface, a value under 2× its label, a `fontSize` that was never measured against the box it sits in (a four-digit one on this rig is the tell), a text not drawn through a type role, or a role whose font asset is built from a variable font. |
| 5 | **Empty state** | Zero / empty / loading renders as nothing instead of as something. |
| 6 | **Contrast** | Text tone does not follow the luminance-0.5 rule above. |
| 7 | **Edge** | Content crosses the safe rect, or clears it by less than `Pad` on any side. |
| 8 | **Affordance** | A tappable thing has no fill/radius/label; disabled does not read disabled. |
| 9 | **9-slice rim** | A sliced sprite has no scale policy in `ui-rules.json` `slices`, a View writes a hand-picked `pixelsPerUnitMultiplier` instead of calling `NineSlice.Apply` after a size write, or the capture reports a `SLICE` line. |

### Who settles which check

The nine are all decidable, but not all by the same tool. Giving a vision judge the ones a grep
already answers buys nothing and adds non-determinism; giving code the ones only a looker can answer
is how a surface ships broken with every assertion green.

| Check | Settled by |
|---|---|
| 1 Ground · 2 Containment · 5 Empty state · 8 Affordance | **looking** — a person, or a vision judge over the capture |
| 3 Rhythm · 6 Contrast | **code** — the layout lint and the layout snapshot; the luminance rule is arithmetic |
| 9 9-slice rim | **code** — `NineSliceLint` on the built capture (exit `1` on a surface not in `sliceDebt`) |
| 4 Hierarchy · 7 Edge | **both** — count the type sizes and read the rect from the layout in code; whether text overflows its box, or content crowds the edge, is a looker's call |

When the surface's spec carries a `## Visual Contract`, settle its rows against the capture with
`docs/framework/recipes/visual-contract-judge.md` — and read that recipe first for what the judge must
not be asked (an exact scale, an exact colour, a `sortingOrder`: those are field assertions), and for
the three rules that keep the loop from running away.

**The 9-slice rim — two policies, one helper.** On the rig ruler a sliced Image draws its rim at
`border / pixelsPerUnitMultiplier` units whatever its size, so a multiplier picked by eye (0.82, 1.85,
2.64…) drifts the rim off the mockup with nothing red. Declare each sliced sprite's policy in
`ui-rules.json` `slices` instead: **`fixed`** — the rim keeps its import pixel width (a frame matched
to one mockup: wood and dialog panels, card geometry, outlines); **`height`** — the caps scale with the
drawn height (`sprite.rect.height / h`: pills, buttons, plaques, ribbons, tracks, row plates the mock
paints whole). `NineSlice.Apply(image, SliceScale)` (`ClassicSpins.PrototypeFramework.Views`) writes
`max(policy, (L+R)/w, (B+T)/h)` — the `max` shrinks the rim uniformly rather than letting Unity squash
one axis — so call it after every size write and mark the node `LayoutDriven(Size)`; a static node is
authored on the prefab at the helper's value. Never a multiplier literal in a View. The capture harness
checks the result (`pf-uigate` › SLICE lines); `sliceTolerance` (default 0.2) is the slack.

**Self-review, every time — and in _play mode_.** A change that draws earns the **visual check**
(`pf-gates` §8a): enter play mode once via `editor-application-set-state`, reach the states you named
**before** entering, and capture each with `screenshot-game-view` — at **FHD in this SKU's own
orientation** (`1080×1920` portrait, `1920×1080` landscape), read off the rig's design rect rather than
hardcoded. Pass that size explicitly to `screenshot-camera`: it defaults to landscape FHD and swaps that
aspect onto the camera, so on a portrait rig it captures an aspect the game never ships. Then walk the eight against the capture, not against your intent, and write down what you saw.
Step the aspect ratios per `pf-world-space` while you are there.

**An edit-mode capture is not the same evidence.** It shows the authored scene, not the running game —
no pooled instances, no bound data, no transition mid-flight. Use it to check a static rig; use a
play-mode capture to claim a screen is finished.

**Bounded, always.** The visual check is *one session with a stated end*. Capture **named states**, not
a playthrough: never sweep hundreds of levels, a whole palette, or a solver run through play mode — see
"Never sweep in play mode" in `pf-gates`. Need confidence over a large set? Capture a **named handful**
(first, last, the spec's extremes) and report it as a sample.

> On macOS these return null while the Editor window is unfocused — and an unfocused Editor's player
> loop does not advance at all, so play mode hangs and draws nothing. That is the cause — ask the user
> to focus the Editor and retry. Never mark the checklist walked on a capture you did not get, and
> never report a blank capture as a visual check.

A feature that draws and whose spec's Verification names no visual check is itself a finding.

## When a placeholder is legitimate

Only on an **explicit human request** — "wireframe", "greybox", "flat colour is fine", "don't spend
time on art". Record that request in the spec's `Boundaries & Constraints`, or in the commit/PR note
when the work has no spec. Absent that trace, an unfinished surface is a review finding, exactly like
a missing test — an approved greybox and a lazy one are indistinguishable in a diff.

Rule 17 governs **composition, not asset production**. Flat tinted rectangles with a coherent palette
and correct rhythm **pass**. The same rectangles on a rig-default ground with no empty slots **fail**.
Nobody is asking you to draw character art.

When the surface does need a bitmap the design package lacks — an illustrated emblem, a prop, or a
plate with an object painted out — do not fake it in code. Load `pf-asset-gen` for
`Tools/pf/asset-gen.py`. Token-drawn chrome stays in an Editor generator.

## Common failures

| Symptom | Cause | Fix |
|---|---|---|
| Game ships on a dark grey nobody chose | Rig camera clear colour treated as the ground | The rig is Ask-First; draw a full-bleed ground under `WorldRoot` instead |
| A grid is one flat panel | Only the container was authored, its slots never were | Check 2 — draw the empty slots |
| Colours drift between two features | Feature two never looked for rung 2 | One LookLibrary; index it, or extend it — never redeclare |
| A `Color[]` ramp sits in a View | Palette treated as view state | Move it to the LookLibrary and index by tier |
| Text renders ~10× too big (the authored value is a four-digit `fontSize`) | A size copied from a doc, an example or another rig instead of measured — here `fontSize` **is** world units | Size from the box, verify with `GetPreferredValues`, store the ratio on the prefab (or the `LookLibrary` when it is shared) |
| A Renderer-drawn TMP renders ~10× too small | `isOrthographic == false` ⇒ TMP's ×0.1 font scale | Tick Orthographic Mode on the component — never compensate with a bigger `fontSize` |
| Grid looks cramped | `gap` solved out of a safe-rect equation | Rhythm first, fit second |
| Every text looks thin next to the mockup, and no weight change helps | The TMP font asset is built from a **variable** font; TMP draws its default instance (often 200 ExtraLight) | Static instance per weight (`Tools/pf/font-check.py --instance`), one font asset each, applied through type roles; `font-check.py --check` in the gate |
| Rows, titles or panels are visibly bigger than the mockup | A design-doc number was followed over the approved mockup | The mockup sets visual size; meet touch floors with an invisible expanded hit area |
